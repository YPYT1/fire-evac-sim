# Git 分支与提交规范

## 分支策略
- `main`：始终保持可部署状态，合并需通过代码审查与自动化测试。
- `develop`：日常集成分支，包含最新完成的功能与修复。
- 功能分支：`feature/<模块>-<描述>`，例如 `feature/backend-session-mgr`。
- 修复分支：`fix/<问题号>-<描述>`。
- 紧急修复：`hotfix/<问题号>-<描述>`，从 `main` 分支创建，修复完成后同时合并回 `main` 与 `develop`。

## 提交流程
1. 每个分支聚焦单一任务或功能，避免混合提交。
2. 提交信息遵循 **Conventional Commits**：
   - `feat: 描述` —— 新功能
   - `fix: 描述` —— 缺陷修复
   - `docs: 描述` —— 文档更新
   - `chore: 描述` —— 构建、配置或依赖变更
   - `refactor/test/style/perf` —— 视具体类型选择
3. 提交信息使用中文或中英结合描述，保持上下文一致。
4. 合并前确保：
   - 本地测试与 linters 全部通过；
   - 更新 `TODO.md` 进度；
   - 在合并请求中列出影响范围与测试结果。

## 代码审查要求
- 每次合并需至少一名团队成员审查。
- 审查重点：功能正确性、性能影响、代码标准、文档与测试是否同步更新。
- 审查意见应在处理后回复确认。

## 标签与版本
- 使用语义化版本：`vMAJOR.MINOR.PATCH`。
- 每次发布在 `main` 分支打标签，并更新变更日志。
